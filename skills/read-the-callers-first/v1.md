# Read the callers first

A function is a contract; its callers are the other signatories.

1. Before changing what a function accepts, returns, or raises,
   search for its callers and read each call site. Note what the
   callers rely on: argument shapes, sentinel values, exceptions
   they catch, ordering they assume.
2. Prefer the repair that keeps the existing contract: fix inside
   the function before changing its signature, and treat a
   signature change as a change to every caller, costed as such.
3. Pay double attention to boundary callers — the ones passing
   user input, empty collections, zero, or the largest values —
   because behaviour changes land on them first.
4. If the task truly requires a contract change, the plan names
   every caller it touches. A caller discovered mid-run that the
   plan did not name is a reason to stop and say so, not to widen
   the edit silently.
